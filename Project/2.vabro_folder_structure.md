# VABRO React Folder Structure -- Interview Explanation

## VABRO React Folder Structure

``` text
vabro-frontend/
│
├── public/
├── src/
│   ├── assets/
│   ├── components/
│   ├── features/
│   ├── pages/
│   ├── hooks/
│   ├── store/
│   ├── services/
│   ├── utils/
│   ├── routes/
│   ├── App.jsx
│   ├── main.jsx
│   └── index.css
│
├── .env
├── package.json
└── vite.config.js
```

------------------------------------------------------------------------

## 1. `public/`

``` text
public/
├── favicon.ico
└── assets/
```

### What goes here?

Static files that need to be served directly.

Examples:

-   Favicon
-   Static images
-   Files that don't need processing by React

### Why do we use it?

It keeps publicly accessible static resources separate from application
code.

### Interview answer

> "The public folder contains static assets that are served directly by
> the application, such as the favicon and other public resources."

------------------------------------------------------------------------

## 2. `src/`

``` text
src/
```

This is the **main application source folder**.

Almost all of our React application code lives inside `src`.

Inside it, we have:

``` text
src/
├── assets/
├── components/
├── features/
├── pages/
├── hooks/
├── store/
├── services/
├── utils/
├── routes/
├── App.jsx
└── main.jsx
```

### Interview answer

> "The src folder contains the actual React application code, including
> components, features, pages, state management, API services, hooks and
> routing."

------------------------------------------------------------------------

## 3. `assets/`

``` text
assets/
├── images/
├── icons/
└── fonts/
```

### What goes here?

Application assets such as:

``` text
images/
    logo.png
    profile.png

icons/
    edit.svg
    delete.svg
    search.svg

fonts/
```

### Why?

Instead of putting images and icons randomly inside feature folders,
commonly used assets are organized centrally.

### Example

``` jsx
import logo from "../../assets/images/logo.png";
```

### Interview answer

> "The assets folder contains reusable application resources such as
> images, icons and fonts."

------------------------------------------------------------------------

## 4. `components/`

This contains **reusable React UI components**.

``` text
components/
├── common/
└── layout/
```

### `components/common/`

``` text
common/
├── Button/
├── Modal/
├── Input/
├── Dropdown/
├── Loader/
└── Table/
```

These components can be used by multiple modules.

For example, the same `Modal` can be used in:

``` text
Projects
Sprint
Kanban
Comments
Automation
```

Instead of creating a separate modal for every module, we create one
reusable component.

### Interview answer

> "The common components folder contains reusable UI components that are
> shared across different modules. This helps us avoid code
> duplication."

------------------------------------------------------------------------

### `components/layout/`

``` text
layout/
├── Header/
├── Sidebar/
└── MainLayout/
```

These components define the overall application layout.

For example:

``` text
             Header
┌───────────────────────────────┐
│                               │
│ Sidebar    Main Content       │
│                               │
│                               │
└───────────────────────────────┘
```

### Why?

The header and sidebar are used across many pages, so we don't want to
recreate them on every page.

### Interview answer

> "The layout folder contains structural components such as the Header,
> Sidebar and MainLayout, which provide the common application layout."

------------------------------------------------------------------------

# 5. `features/` ⭐

This is one of the most important folders for VABRO.

``` text
features/
├── auth/
├── projects/
├── workspace/
├── sprint/
├── kanban/
├── okr/
├── calendar/
├── comments/
├── automation/
├── reporting/
└── dashboard/
```

Each folder represents a **business module**.

For example:

``` text
features/projects/
```

contains everything related to Projects.

------------------------------------------------------------------------

## Why use `features/`?

VABRO is a large application.

If we put every component into one giant `components` folder, eventually
we could have:

``` text
components/
├── ProjectCard.jsx
├── SprintCard.jsx
├── KanbanCard.jsx
├── OkrCard.jsx
├── Comment.jsx
├── AutomationRule.jsx
├── DashboardChart.jsx
...
```

It becomes difficult to maintain.

Instead:

``` text
features/
├── projects/
├── sprint/
├── kanban/
├── comments/
└── automation/
```

Now each module is isolated.

### Interview answer

> "Because VABRO has multiple business modules, we organize the
> application feature-wise. Each feature contains the components, pages,
> state and API logic related to that particular business
> functionality."

------------------------------------------------------------------------

# 6. Example: `features/projects/`

For example:

``` text
projects/
├── components/
│   ├── ProjectList.jsx
│   ├── ProjectCard.jsx
│   ├── ProjectForm.jsx
│   └── ProjectDetails.jsx
│
├── pages/
│   ├── ProjectListPage.jsx
│   └── ProjectDetailsPage.jsx
│
├── projectSlice.js
└── projectApi.js
```

### `components/`

Project-specific components.

For example:

``` text
ProjectCard
ProjectForm
ProjectDetails
ProjectList
```

These aren't necessarily useful outside the Project module.

### `pages/`

Complete screens related to Projects.

### `projectSlice.js`

Redux state related to Projects.

For example:

``` text
projects
selectedProject
loading
error
```

### `projectApi.js`

Project-related API operations.

For example:

``` text
getProjects()
getProjectById()
createProject()
updateProject()
deleteProject()
```

### Interview answer

> "Inside each feature, we keep module-specific components, pages, Redux
> state and API logic together. For example, the Projects feature
> contains project components, project pages, project Redux state and
> project API operations."

------------------------------------------------------------------------

# 7. `pages/`

``` text
pages/
├── Login/
├── Dashboard/
├── Projects/
└── NotFound/
```

A **page represents a complete screen**.

For example:

``` text
ProjectsPage
```

may combine:

``` text
ProjectHeader
ProjectFilters
ProjectList
Pagination
```

So:

``` text
Page
 ↓
Multiple Components
 ↓
Complete Screen
```

### Difference between `components` and `pages`

**Component:**

``` text
ProjectCard
```

Small reusable UI.

**Page:**

``` text
ProjectsPage
```

Complete screen composed of multiple components.

### Interview answer

> "The pages folder contains route-level screens. A page generally
> combines multiple components and represents a complete user-facing
> screen."

------------------------------------------------------------------------

# 8. `hooks/`

``` text
hooks/
├── useAuth.js
├── useDebounce.js
└── usePermission.js
```

This contains **custom React hooks**.

Suppose we have permission logic used in many places.

Instead of repeating it:

``` jsx
if (user.role === "admin") {
   ...
}
```

we can create:

``` jsx
const { hasPermission } = usePermission();
```

Similarly:

``` text
useAuth()
useDebounce()
usePermission()
```

### Why?

To reuse React-related logic.

### Interview answer

> "The hooks folder contains custom hooks that encapsulate reusable
> React logic, such as authentication, permission checking and
> debouncing."

------------------------------------------------------------------------

# 9. `store/`

``` text
store/
├── store.js
└── rootReducer.js
```

This is related to **Redux**.

### `store.js`

Creates and configures the Redux store.

Conceptually:

``` text
Redux Store
│
├── auth
├── project
├── workspace
├── sprint
└── ...
```

### `rootReducer.js`

Combines different reducers.

For example:

``` text
authReducer
projectReducer
workspaceReducer
```

into the application's Redux state.

### Important interview point

Don't say:

> "We store everything in Redux."

Instead say:

> "We use Redux for state that needs to be shared across different
> components or modules. Component-specific UI state is generally
> handled using React local state."

------------------------------------------------------------------------

# 10. `services/`

``` text
services/
├── api.js
├── authService.js
└── projectService.js
```

This layer handles communication with backend APIs.

For example:

``` text
React Component
      ↓
Service/API
      ↓
Backend REST API
      ↓
Database
```

Example:

``` javascript
projectService.getProjects();
```

The component doesn't need to know all the details of the HTTP request.

### Why?

It separates:

``` text
UI logic
```

from:

``` text
API communication
```

### Interview answer

> "The services folder contains API and backend communication logic. It
> keeps API-related code separate from UI components and makes the code
> easier to maintain."

------------------------------------------------------------------------

# 11. `utils/`

``` text
utils/
├── validation.js
├── dateUtils.js
├── formatters.js
└── constants.js
```

Contains generic helper functions.

For example:

``` javascript
formatDate()
validateEmail()
formatNumber()
```

These functions aren't tied to a particular React component.

### Example

If multiple modules need date formatting:

``` text
Projects
Calendar
Sprint
Reporting
```

instead of implementing date formatting repeatedly, we create:

``` text
utils/dateUtils.js
```

### Interview answer

> "The utils folder contains reusable helper functions and constants
> that are independent of a particular feature."

------------------------------------------------------------------------

# 12. `routes/`

``` text
routes/
├── AppRoutes.jsx
├── ProtectedRoute.jsx
└── routeConfig.js
```

This manages application routing.

For example:

``` text
/login
/dashboard
/projects
/projects/:projectId
/sprint
/kanban
/okr
/calendar
```

------------------------------------------------------------------------

## `ProtectedRoute.jsx`

Used for routes that require authentication.

Flow:

``` text
User
 ↓
Protected Route
 ↓
Is user authenticated?
 ↓
 ┌─────────────┐
 ↓             ↓
YES            NO
 ↓             ↓
Page           Login
```

### Interview answer

> "The routes folder centralizes application routing. We also use
> protected routes to prevent unauthenticated users from accessing
> restricted VABRO pages."

------------------------------------------------------------------------

# 13. `App.jsx`

This is the **main application component**.

Conceptually:

``` text
App.jsx
   ↓
Routes
   ↓
Layout
   ↓
Page
   ↓
Components
```

It provides the high-level structure of the application.

### Interview answer

> "App.jsx acts as the root React component where the main application
> structure and routing are connected."

------------------------------------------------------------------------

# 14. `main.jsx`

This is the **entry point** of the React application.

Conceptually:

``` text
main.jsx
   ↓
ReactDOM.createRoot()
   ↓
App
```

It can also wrap the application with providers.

For example:

``` text
Redux Provider
       ↓
BrowserRouter
       ↓
App
```

### Interview answer

> "main.jsx is the entry point of the React application. It creates the
> React root and renders App. Global providers such as Redux Provider
> and Router can also be configured here."

------------------------------------------------------------------------

# 15. `index.css`

Contains global styles.

For example:

``` text
body
button
input
global classes
CSS variables
```

### Why?

Styles that need to apply globally can be maintained here instead of
repeating them across components.

------------------------------------------------------------------------

# 16. `.env`

Contains environment-specific configuration.

For example:

``` text
API_URL
```

Instead of hardcoding:

``` javascript
"https://production-api.com"
```

we can use an environment variable.

### Interview answer

> "Environment variables allow us to keep environment-specific
> configuration such as API URLs outside the source code."

------------------------------------------------------------------------

# 17. `package.json`

Contains:

-   Project information
-   Dependencies
-   Scripts
-   Package versions

For example:

``` text
react

react-router-dom
redux

```

If VABRO uses Vite, this contains Vite configuration.

It can be used for:

-   Plugins
-   Aliases

# ⭐ Interview Answer

If the interviewer asks:

**"Can you explain the folder structure of your VABRO React
application?"**

You can answer:

> "In VABRO, we follow a modular and feature-based React structure. The
> application starts from `main.jsx`, which renders `App.jsx`. Routing
> determines which page needs to be displayed. Each page is composed of
> reusable common components and feature-specific components.
>
> Business modules such as Projects, Sprint, Kanban, OKR, Comments,
> Automation and Reporting are organized under the `features` folder.
> For shared application state, we use Redux, while component-specific
> state is handled locally. API communication is separated into service
> or API files, reusable React logic is handled through custom hooks,
> and common helper functions are maintained in the `utils` folder.
>
> This separation makes the code easier to maintain, reuse and scale,
> especially because VABRO contains multiple business modules."
