# What is the services folder?

In VABRO, we used the services folder to keep all API-related logic separate from React components. Each module had its own service file, such as projectService, sprintService, dashboardService, and authService. These files contained functions for fetching, creating, updating, and deleting data. The services layer handled API requests, attached authentication tokens, processed responses, and managed error handling. This approach kept components focused on UI rendering and improved code reusability, maintainability, and scalability.

The services folder contains all code related to communicating with the backend APIs.

Instead of writing API calls inside every React component, we keep them in separate files.

## Bad Approach

```jsx
function Projects() {
  useEffect(() => {
    fetch("/api/projects")
      .then((res) => res.json())
      .then((data) => console.log(data));
  }, []);
}
```

If multiple pages need project data, you'll end up repeating the same API code everywhere.

## Better Approach

Create a service:

```jsx
// services/projectService.js

export const getProjects = async () => {
  const response = await fetch("/api/projects");
  return response.json();
};
```

Now use it in any component:

```jsx
import { getProjects } from "../services/projectService";

function Projects() {
  useEffect(() => {
    getProjects().then((data) => {
      console.log(data);
    });
  }, []);
}
```

The component only focuses on UI.

The service handles backend communication.

### Example: projectService.ts

```jsx
import axios from "axios";

export const getProjects = () => {
  return axios.get("/api/projects");
};

export const createProject = (payload) => {
  return axios.post("/api/projects", payload);
};

export const updateProject = (id, payload) => {
  return axios.put(`/api/projects/${id}`, payload);
};

export const deleteProject = (id) => {
  return axios.delete(`/api/projects/${id}`);
};
```

All Project APIs stay in one place.

## What Does Request Handling Mean?

Before sending a request, sometimes we need to:

### Add JWT Token

```jsx
headers: {
  Authorization: `Bearer ${token}`
}
```

### Add Query Params

```text
/api/projects?page=1&limit=10
```

### Send Request Body

```jsx
{
  name: "Frontend Revamp",
  status: "Active"
}
```

This preparation is called request handling.

## What Does Response Transformation Mean?

Backend may return:

```jsx
{
  success: true,
  data: {
    projects: [...]
  }
}
```

We may transform it into:

```jsx
return response.data.projects;
```

So components receive clean data.

```jsx
const projects = await getProjects();
```

Instead of:

```jsx
response.data.data.projects
```

everywhere.

## What Does Error Handling Mean?

Suppose API fails.

```jsx
try {
  const response = await axios.get("/api/projects");
  return response.data;
} catch (error) {
  console.error(error);
}
```

Or:

```jsx
if (error.response.status === 401) {
  logoutUser();
}
```

Or show:

```text
"Something went wrong"
```

This logic is usually kept in services.

# Let's understand with a real VABRO-style example.

## Step 1: Create Service

```jsx
// services/projectService.js

import axios from "axios";

export const getProjects = () => {
  return axios.get("/api/projects");
};
```

This function only knows how to fetch projects from the backend.

## Step 2: Use Service Inside Component

```jsx
import React, { useEffect, useState } from "react";
import { getProjects } from "../services/projectService";

function Projects() {
  const [projects, setProjects] = useState([]);

  useEffect(() => {
    fetchProjects();
  }, []);

  const fetchProjects = async () => {
    try {
      const response = await getProjects();

      setProjects(response.data);
    } catch (error) {
      console.error("Failed to fetch projects", error);
    }
  };

  return (
    <div>
      <h2>Projects</h2>

      {projects.map((project) => (
        <p key={project.id}>{project.name}</p>
      ))}
    </div>
  );
}

export default Projects;
```

## Flow

```text
Component
   ↓
getProjects()
   ↓
projectService
   ↓
Backend API
   ↓
Response
   ↓
setProjects()
   ↓
UI Re-render
```

# Real Redux Toolkit Flow (Most Common in Large Projects)

In VABRO, you probably wouldn't call the service directly from every component.

Instead:

```text
Component
   ↓
Dispatch Action
   ↓
createAsyncThunk
   ↓
projectService
   ↓
Backend API
   ↓
Redux Store Update
   ↓
Component Gets Data
```

### projectService

```jsx
export const getProjects = () => {
  return axios.get("/api/projects");
};
```

### projectSlice

```jsx
export const fetchProjects = createAsyncThunk(
  "projects/fetchProjects",
  async () => {
    const response = await getProjects();

    return response.data;
  }
);
```

### Component

```jsx
const dispatch = useDispatch();

useEffect(() => {
  dispatch(fetchProjects());
}, []);
```

### Read Data

```jsx
const projects = useSelector(
  (state) => state.projects.data
);
```

# Interview Answer

In React, components usually don't make API calls directly. Instead, we create reusable functions inside the services folder. For example, projectService contains functions like getProjects, createProject, updateProject, and deleteProject. Components call these service functions whenever data is needed. In larger applications like VABRO, the component dispatches a Redux action, which calls the service function through createAsyncThunk. The API response is then stored in Redux, and components read the data using useSelector. This keeps API logic separate from UI code and makes the application easier to maintain.

The important thing to remember:

Service = API Logic  
Redux = State Management  
Component = UI

Each layer has a separate responsibility. This is how most enterprise React applications are structured.
