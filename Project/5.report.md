# VABRO -- Reports & Analytics Module
[VAbro report figma ](https://www.figma.com/design/c8Sm4f63fPjvMKPsC1YplT/scaling-scrum-prod-team-audit?node-id=5098-3190&p=f&m=dev)
## 1. Purpose of the Reports Module

The Reports module in VABRO provides users with a visual and interactive way to analyze project, task, sprint, and team-related data. It converts raw data from REST APIs into meaningful charts and reports, helping users quickly understand project progress, task distribution, team performance, and activity trends.

The module uses Chart.js and Recharts to create visualizations such as line, bar, and doughnut charts, along with features like tooltips, legends, filters, and date-range selection. It also supports large datasets by allowing horizontal scrolling while keeping the Y-axis visible for better readability.

### 2.2 Recharts

For some reporting requirements, Recharts was used because it provides
React-oriented chart components and gives more control over individual
chart elements.

Example:

``` jsx
<ResponsiveContainer width="100%" height={400}>
  <LineChart data={reportData}>
    <XAxis dataKey="date" />
    <YAxis />
    <Tooltip />
    <Line dataKey="completedTasks" />
  </LineChart>
</ResponsiveContainer>
```

The component-based approach made it easier to control the layout, axes,
scrolling area, and responsive behavior.

# 4. Major Challenge -- Large X-Axis Data

One of the important challenges we faced in the VABRO Reports module was
handling charts with a large number of X-axis data points.

For example, a report may contain data for many dates:


Displaying all the data points in the available screen width makes the
chart crowded and difficult to read.

Therefore, we needed the following behavior:

> The Y-axis should remain fixed while the chart's X-axis and data area
> should scroll horizontally.

The expected layout was:

``` text
┌────────┬─────────────────────────────────────┐
│        │                                     │
│ Fixed  │        Horizontally Scrollable     │
│ Y-Axis │             Chart Area              │
│        │                                     │
│  100   │       █                             │
│   80   │    █  █       █                     │
│   60   │    █  █       █       █             │
│   40   │ █  █  █       █       █             │
│   20   │ █  █  █       █       █             │
│    0   │─────────────────────────────────────│
│        │ Jan  Feb  Mar  Apr  May →           │
└────────┴─────────────────────────────────────┘
                 ← horizontal scroll
```

# 5. Problem with the Initial Chart Implementation

The challenge was not simply adding a horizontal scrollbar.

If the complete chart is placed inside:

``` css
overflow-x: auto;
```

then the complete chart, including the Y-axis, moves horizontally.

For example:

``` text
← everything moves →

       Y-axis | Chart Data
```

This creates a poor user experience because users lose the Y-axis
reference while scrolling through the report.

The desired behavior was:

``` text
Y-axis | Chart Data → scroll
       |
       | █ █ █ █ █ █
       | █ █ █ █ █ █
       | █ █ █ █ █ █
```

------------------------------------------------------------------------

# 7. Solution Using Recharts

We solved the problem by separating the fixed Y-axis area from the
scrollable chart area.

Conceptually, the structure became:

``` text
┌────────┬─────────────────────────────────────┐
│        │                                     │
│ Fixed  │        Horizontally Scrollable     │
│ Y-Axis │             Chart Area              │
│        │                                     │
│  100   │  █    █                             │
│   80   │  █    █       █                     │
│   60   │  █    █       █       █             │
│   40   │  █    █       █       █             │
│   20   │  █    █       █       █             │
│    0   │  █    █       █       █             │
│        │  Jan  Feb  Mar  Apr  May →          │
└────────┴─────────────────────────────────────┘
                 ← horizontal scroll
```

The basic implementation concept was:

``` jsx
<div className="report-chart">

  <div className="fixed-y-axis">
    {/* Fixed Y Axis */}
  </div>

  <div className="scrollable-chart">
    <LineChart>
      {/* X Axis + Chart */}
    </LineChart>
  </div>

</div>
```

The chart itself can have a larger internal width:

``` jsx
<LineChart
  width={1500}
  height={400}
  data={reportData}
>
```

The parent container then controls horizontal scrolling.

# 9. Benefits of the Solution

The solution provided several usability improvements:

-   Y-axis remains visible during horizontal scrolling.
-   Large datasets can be displayed without compressing all data into a
    small area.
-   Users can inspect a large time range more easily.
-   Chart labels remain more readable.
-   The chart layout becomes more suitable for dashboards and analytics
    pages.
-   The reporting interface becomes easier to use on smaller screens.
-   The chart area can have a larger internal width while remaining
    inside a responsive container.

# 13. Data Transformation Before Chart Rendering

Backend data does not always have the exact structure required by a
chart library.

For example, the API might return:

``` json
[
  {
    "createdAt": "2026-09-01",
    "taskCount": 25
  },
  {
    "createdAt": "2026-09-02",
    "taskCount": 35
  }
]
```

The frontend can transform it into a chart-friendly structure:

``` js
const chartData = apiData.map(item => ({
  date: item.createdAt,
  tasks: item.taskCount
}));
```

Then the chart can consume:

``` jsx
<LineChart data={chartData}>
  <XAxis dataKey="date" />
  <YAxis />
  <Tooltip />

  <Line dataKey="tasks" />
</LineChart>
```

This separation makes the chart component easier to maintain because the
chart receives data in a predictable format.
