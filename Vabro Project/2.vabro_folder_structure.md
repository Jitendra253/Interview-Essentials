## 2. `vabro-frontend/` --- Project root

This is the root directory of the frontend project. It contains the
source code, public files, dependency definitions, environment
configuration, and build-tool configuration.

### Main items

- `public/`: files served directly as static assets.
- `src/`: application source code.
- `.env`: environment-specific configuration.
- `package.json`: project scripts and dependencies.
- `vite.config.js`: Vite development and build configuration.

**Interview answer:**

> "The project root contains the React application source, static
> assets, dependency configuration, environment variables, and Vite
> configuration."

## 3. `public/` --- Public static files

### Purpose

Stores files that should be served directly rather than imported into
JavaScript and processed by Vite.

Possible examples include:

- `favicon.ico`
- Publicly accessible static files
- Files that need a stable URL or filename

For example, a file at `public/favicon.ico` is generally available at
`/favicon.ico`.

### When to use it

Use `public/` when a file needs to be served as-is. If an image is
imported into a component and should participate in Vite's asset
processing, it usually belongs in `src/assets/`.

**Interview answer:**

> "The public folder contains static resources that Vite serves
> directly, such as the favicon or files that need a stable public
> path."

## 4. `src/` --- Application source code

This is the main folder for the React application. Most code that
defines the UI, application behavior, routing, state, and API
communication lives here.

Its subfolders separate code by responsibility:

- `assets/`: images, icons, and fonts.
- `components/`: reusable UI building blocks.
- `pages/`: complete route-level screens.
- `services/`: backend API requests.
- `store/`: shared Redux state,
- `hooks/`: reusable React logic.
- `utils/`: general helper functions.
- `routes/`: route definitions and frontend route guards.

**Interview answer:**

> "The src folder contains the application code, organized into UI
> components, pages, services, state management, hooks, utilities, and
> routes."

## 5. `src/assets/` --- Images, icons, and fonts

### Purpose

Keeps visual resources used by the frontend in one place.

Possible organization:

```text
assets/
├── images/
├── icons/
└── fonts/
```

Examples include a company logo, profile placeholder, SVG icons, and
font files.

### Example


- Makes files easier to find.
- Avoids scattering shared visual resources throughout the project.
- Lets Vite process imported assets during the build.

**Interview answer:**

> "The assets folder contains visual resources such as images, icons,

## 6. `src/components/` --- Reusable UI building blocks

A component is a self-contained part of the user interface. Components
can be combined to build pages.

In this structure, components are grouped into common UI, layout UI, and
module-specific UI.

### 6.1 `components/common/`

Contains generic components that can be reused in different areas of the
application.

#### `Button.jsx`

A reusable button component can standardize appearance and behavior for
actions such as Save, Cancel, Delete, and Create.

Potential benefits:

- Consistent styling.
- Shared disabled and loading states.
- Less duplicated markup.
- Easier global UI changes.

#### `Modal.jsx`

A reusable modal shell can display different content, such as a
create-project form, edit form, or confirmation message.

The modal can accept props such as `isOpen`, `onClose`, and `children`,
depending on its implementation.

#### `Loader.jsx`

Displays a loading indicator while data is being fetched or an operation
is in progress.

It may be used for a full page, a table, a chart, or a button, depending
on how it is designed.

**Other common components** could include inputs, dropdowns, tooltips,
pagination, and tables, but they are not listed in the supplied
structure and are not required unless the app needs them.

**Interview answer:**

> "The common components folder contains generic UI elements such as
> buttons, modals, and loaders that can be reused across multiple pages
> and modules."

### 6.2 `components/layout/`

Contains components that define the shared structure around pages.

#### `Header.jsx`

May display the application logo, navigation controls, user menu, or

#### `Sidebar.jsx`

May provide navigation links to modules such as Dashboard, Projects,

A shared header and sidebar mean pages can reuse the same application

### How do common and module-specific components differ?

- Put a component in `common/` when it is generic and useful across

- Put a component in `projects/`, `kanban/`, or `dashboard/` when it

**Interview answer:**

## 8. `src/services/` --- API communication

The services folder contains functions that communicate with the
backend, usually through HTTP requests to REST APIs.

### `apiRequest.js`

Can hold shared request configuration, such as:

- Base API URL.
- Common headers.
- Shared fetch or Axios setup.
- Common request or response handling, if implemented.

Avoid putting every module's business logic into this single file. Its
purpose is to provide shared API infrastructure.

### `authService.js`

Contains authentication-related requests, for example:

- Sign in.
- Sign out, if supported by the backend.
- Retrieve the current user, if supported.

### `projectService.js`

Contains project-related API operations, for example:

- Fetch projects.
- Fetch project details.
- Create a project.
- Update a project.
- Delete a project, if the API supports it.

### `sprintService.js`

Contains sprint-related API operations, such as fetching sprints or
creating and updating them, according to the backend API.

### `reportService.js`

Contains requests for reporting data, such as dashboard metrics or
project and sprint analytics.

### Simplified example

```javascript
// projectService.js
export async function getProjects() {
  const response = await fetch("/api/projects");

  if (!response.ok) {
    throw new Error("Unable to load projects");
  }

  return response.json();
}
```

This example uses a placeholder endpoint. In a real application, the URL
and request options must match the backend contract.

### Why keep API calls in services?

- Avoids repeating request code across components.
- Keeps UI rendering separate from HTTP details.
- Makes request logic easier to test and maintain.
- Allows several components to reuse the same API function.

**Interview answer:**

> "The services folder handles communication with backend REST APIs. The
> shared apiRequest file contains common request configuration, while
> authentication, project, sprint, and report services group their
> respective API operations."

## 9. `src/store/` --- Shared application state with Redux Toolkit

This folder is for Redux state management if the application uses Redux
Toolkit.

### `store.js`

Creates and configures the Redux store. It registers reducers and
provides a single store that React components can access through the
Redux Provider.

Conceptual example:

```javascript
import { configureStore } from "@reduxjs/toolkit";
import authReducer from "./slices/authSlice";
import projectReducer from "./slices/projectSlice";
import sprintReducer from "./slices/sprintSlice";
import dashboardReducer from "./slices/dashboardSlice";

export const store = configureStore({
  reducer: {
    auth: authReducer,
    projects: projectReducer,
    sprints: sprintReducer,
    dashboard: dashboardReducer,
  },
});
```

This example assumes each slice exports a default reducer and that the
application uses Redux Toolkit. Adjust it to match the actual slice
exports and state design.

### `store/slices/`

A Redux slice groups the initial state, reducers, and generated actions
for a particular state area.

#### `authSlice.js`

May manage authentication-related frontend state, such as the current
user or authentication status. Token storage and session handling depend
on the actual authentication implementation.

#### `projectSlice.js`

May manage shared project state, such as project lists, selected project
details, and request status.

#### `sprintSlice.js`

May manage shared sprint data and its request status.

#### `dashboardSlice.js`

May manage dashboard data shared across widgets or screens, where
centralized state is useful.

### What belongs in Redux and what belongs in local state?

suitable for

Shared sprint data. Temporary form input.

application.

---

This is a guideline, not a strict rule. Use Redux when shared state and
its update flow benefit from central management; not every API response
must be stored in Redux.

### Redux and services work together

A common pattern is:

```text
Page or component
       ↓
Dispatch async thunk
       ↓
Thunk calls service function
       ↓
Backend API returns data or error
       ↓
Thunk is fulfilled or rejected
       ↓
Slice state is updated
       ↓
Component reads state and re-renders
```

An async thunk can handle request lifecycle actions such as pending,
fulfilled, and rejected. A component can then display a loader, data, or
an error message based on the state.

**Interview answer:**

> "The store folder configures Redux Toolkit and registers the reducers.
> The slices folder keeps state and reducer logic organized by area,
> such as authentication, projects, sprints, and dashboard. We use Redux
> for shared application state and React local state for
> component-specific interactions."

## 10. `src/hooks/` --- Reusable React logic

Custom hooks let components reuse stateful React logic without
duplicating it.

The supplied tree leaves this folder empty, so the following are
examples of hooks that could be added if needed.

### Possible examples

- `useAuth()` --- a convenient interface to authentication state or
  actions.
- `useDebounce()` --- delays a changing value until updates pause,
  useful for search.
- `usePermission()` --- provides reusable frontend permission checks.

A custom hook should follow the Rules of Hooks and normally have a name
beginning with `use`.

### Why use hooks?

- Reuse logic across components.
- Keep components focused on rendering.
- Centralize repeated behavior.

**Interview answer:**

> "The hooks folder is for reusable React logic, such as debouncing a
> search value or accessing authentication and permission-related
> state."

Frontend permission checks improve the UI experience, but the backend
must enforce authorization for protected operations.

### `ProtectedRoute.jsx`

Can guard frontend routes that require an authenticated user. Depending

Conceptual flow:

```text
User visits protected route
          ↓

          ↓
```

## 19. How the folders work together

Consider loading the Projects page:

```text
1. main.jsx mounts the React application.
2. App.jsx connects the application structure.
3. AppRoutes.jsx matches the current URL.
4. Projects.jsx renders the Projects screen.
5. Project components render lists, filters, cards, or forms.
6. A service function calls the backend API when project data is needed.
7. If the request uses Redux, an async thunk coordinates the request and updates the slice.
8. The page reads the resulting state and renders the current data.
```

The Redux store is available to components under its Provider; not every
request has to use Redux. A page can also manage a local request with
React state when the result is only needed locally.
