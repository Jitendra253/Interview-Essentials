# How to handle common api calls and error handling.

# Best Practice for API Call

In my React applications, I handle API calls using a separate services folder, where I maintain a common apiRequest function which handles the base URL, headers, and HTTP error.

And also I create individual service files for different modules, such as projects, User Story and sprints.

When data needs to be shared across multiple components, I use Redux Toolkit with createAsyncThunk to call the service function. Then, in extraReducers, I handle three states: pending, fulfilled, and rejected. When the request is pending, I set loading to true; when it succeeds, I store the response data in the Redux store; and when it fails, I store the error message. Finally, I use useSelector to access the data, loading, and error states in my components, and useDispatch to trigger API requests.

When API data is required only within a particular component, I use a custom hook to manage API calls. I keep the API logic in a separate services folder and create a reusable custom hook using useState, useEffect, and useCallback. The hook manages data, loading, and error states and provides an execute function to trigger or retry the API request. When the request starts, I set loading to true; when it succeeds, I store the response data; and if it fails, I capture the error message. Finally, the component uses the returned states to display a loader, error message with a retry option, or the actual data.

# When to use Context API and when to use Redux

1. When to use Context API
   Use Context API when your application has relatively simple shared state that multiple components need to access.
   Examples:

- Theme: light mode and dark mode.
- Language: English, Hindi, etc.
- Logged-in user information.
- Simple authentication state.

2. When to use Redux Toolkit
   Use Redux Toolkit when your application has complex shared state, many related updates, or asynchronous workflows that benefit from centralized management.
   Examples:

- Project and sprint data shared across screens.
- Complex dashboard state.
- Multiple related modules that depend on shared data.
- API loading, success, and error states managed through async thunks.

```javascript
import { useTranslation } from "react-i18next";

function Header() {
  const { t, i18n } = useTranslation();

  const changeLanguage = (language) => {
    i18n.changeLanguage(language);
    localStorage.setItem("language", language);
  };

  return (
    <div>
      <h1>{t("welcome")}</h1>
      <button onClick={() => changeLanguage("en")}>English</button>
      <button onClick={() => changeLanguage("hi")}>Hindi</button>
    </div>
  );
}

export default Header;
```

I would use i18next and react-i18next to implement multilingual support in VABRO. I would maintain separate translation JSON files for each language and use the t() function to display translated text. When users change the language, the UI updates automatically, and I save their language preference in local storage. If multiple components need the selected language, I can manage that shared preference through Context API

# Role-Based Access Control (RBAC) in React

## 1. What is RBAC?

Role-Based Access Control (RBAC) means giving users access to pages and actions based on their roles, such as **Admin**, **Manager**, and **Employee**.

In VABRO, different users may have different permissions depending on their responsibilities.

## 2. How It Works

1. After login, the backend verifies the user and returns their role and permissions.
2. The frontend stores the authenticated user's information using a state solution such as Redux Toolkit or Context API.
3. React displays the menus, pages, and buttons allowed for that user.
4. Protected routes restrict navigation to authorized pages.
5. The backend independently checks permissions for every protected API request.

**Important:** Frontend checks improve the user experience, but backend authorization is essential for security.

## 3. Simple React Example

```jsx
const user = {
  name: "Jitendra",
  role: "Admin",
};

function Dashboard() {
  return (
    <div>
      <h1>Dashboard</h1>

      {user.role === "Admin" && <button>Manage Users</button>}

      {user.role === "Manager" && <button>Manage Projects</button>}
    </div>
  );
}
```

In this example, an Admin sees the **Manage Users** button, while a Manager sees the **Manage Projects** button.

## 4. Protected Route Example

```jsx
import { Navigate, Outlet } from "react-router-dom";

function ProtectedRoute({ allowedRoles, user }) {
  if (!user) {
    return <Navigate to="/login" replace />;
  }

  if (!allowedRoles.includes(user.role)) {
    return <Navigate to="/unauthorized" replace />;
  }

  return <Outlet />;
}
```

### Usage

```jsx
<Route element={<ProtectedRoute user={user} allowedRoles={["Admin"]} />}>
  <Route path="/users" element={<UsersPage />} />
</Route>
```

Only an authenticated user whose role is `Admin` can access the Users page through this route.

## 5. Interview Answer

“In VABRO, I would implement Role-Based Access Control using roles and permissions. After login, the backend provides the authenticated user's role and permissions. I manage this information using Redux Toolkit or Context API and conditionally render menus, buttons, and pages. I use protected routes in React Router to restrict navigation. Most importantly, the backend independently validates permissions for every protected API request to ensure security.”
